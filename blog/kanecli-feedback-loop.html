From KaneCLI evidence to an improved verification loop

Engineering retrospective · 25 November 2026 · AI-assisted, human-operated

The first genuine KaneCLI run checked three user-visible scenarios: clean CSV produced PASS with two records, the invalid sample produced FAIL with three issues, and reset restored PASS. Kane also checked that export was disabled before validation. The run passed; it did not discover a software defect.

Reviewing the actual test evidence revealed an important coverage gap: the exported JSON content had not been inspected. An AI coding assistant changed the app to mark the report source as LOCAL_BROWSER, verifiedByKane as false and transactionSettled as false. The independent Chromium suite was extended to parse the actual downloaded file and assert these fields.

After redeployment, a second genuine KaneCLI run checked the clean, failing and reset scenarios, confirmed the export button became enabled and triggered a download. Kane did not inspect the downloaded JSON content. Independent Chromium CI performed that assertion separately.

The distinction matters. A passing browser scenario is evidence for its specific assertions, not proof of payment or regulatory approval. The project demonstrates a bounded feedback loop: real Kane result, AI-assisted change, redeployment, real Kane retest, and independently verified report contents.
